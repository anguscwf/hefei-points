# ADR-0005：生产迁移必须先取得可验证的旧库快照

- 状态：已接受
- 日期：2026-08-23
- 决策人：安总

## 背景

原备份命令复用应用数据库连接，而该连接在打开数据库时会自动执行迁移。因此它只能备份迁移后的数据库，不能满足“旧库备份 → 校验 → 执行迁移”的发布顺序。

SQLite WAL 模式下直接复制单个主数据库文件也可能遗漏已提交 WAL 内容；盲目复制 `-shm` 不是可靠恢复方案。

## 决定

- 新增独立的 `npm run backup:pre-migration`。脚本直接使用 `node:sqlite` 打开源库，不导入应用连接模块，也不执行任何迁移。
- 使用 SQLite `VACUUM INTO` 创建事务一致的快照；该方式会包含已提交 WAL 内容。快照完成后执行 `PRAGMA integrity_check`、`PRAGMA foreign_key_check`，核对家庭、用户、账户和流水数量。
- 生成 `manifest.json`，记录快照 SHA-256、全库逻辑内容 SHA-256、字节数、已应用/待执行迁移和业务计数。逻辑摘要按表结构、列和值的确定性顺序计算，只保存摘要，不输出业务内容。清单及快照位于被 Git 忽略的 `backups/`。
- 生产环境若检测到存量业务数据和待执行迁移，必须设置 `PRE_MIGRATION_BACKUP_MANIFEST`。应用连接会验证清单、快照哈希、完整性、迁移集合、业务计数和当前源库逻辑摘要；缺失、陈旧或不匹配时拒绝迁移。
- 新建空库不要求旧库快照；已经没有待执行迁移的正常重启也不要求重复提供清单。

## 影响

- 发布人员不能再通过“直接启动新代码”绕过迁移前备份。
- 备份脚本不会读取应用业务配置，不会写入源库逻辑数据，也不会在源码仓库产生可跟踪文件。
- 原 `npm run backup` 仍用于日常迁移后备份，不能替代迁移前快照。
- 发布时仍应先停止业务写入；清单业务计数校验可以发现常见的备份后继续写入，但不是在线双写一致性协议。

## 发布顺序

1. 停止业务写入；
2. 运行 `npm run backup:pre-migration -- --database <旧库> --backup-root <备份目录>`；
3. 保存输出的 `manifest.json` 路径与 SHA-256；
4. 设置 `PRE_MIGRATION_BACKUP_MANIFEST=<manifest.json>`；
5. 启动兼容代码执行迁移；
6. 核对 `integrity_check`、迁移版本、家庭数、余额与流水；
7. 按功能门逐项启用，不在迁移完成时自动开放儿童功能。
