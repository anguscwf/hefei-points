# ADR-0011：积分申请文字留存与监护安全放弃决策边界

- 状态：提议中（未接受，不授权实施）
- 日期：2026-08-29
- 决策人：待产品、合规与安全负责人共同确认
- 实施授权：无

## 背景与目标

ADR-0007 已定义积分申请、审批、不可变事件和来源流水；ADR-0008 仍把删除执行固定在 `blocked_policy`；ADR-0010 只建立来源设备专属的历史操作回执对账，并明确 `not_observed` 不是 no-effect 证明。S20b/S20c 进一步完成当前详情与列表的只读界面围栏，但没有开放补充、取消、重新提交，也没有新增持久 mutation intent 或 coordinator。

在未来设计这些写操作前，必须先回答两组相互关联、但不能混为一谈的问题：

1. 儿童申报文字、历次补充文字、监护人留言、审计事件、幂等证据、设备本地恢复材料、导出和备份分别保留多久、从何时起算、到期如何处置；
2. 当设备无法证明某次写操作是否已执行时，谁可以在什么证据下授权停止恢复，以及怎样保证这不被误解为“服务端未执行”。

本 ADR 是供产品、合规和安全共同评审的唯一 S20d 决策包。当前没有形成已接受的留存期限、安全放弃条件或实现授权；所有标记为“待定（阻断）”的格子都必须由有权责任人填实，不能由开发者、客户端或测试默认补全。

## 继承且不得放宽的边界

- 家庭角色不等于监护授权；监护关系、当前授权、儿童隐私状态、设备绑定和会话必须继续分别校验。任一监护授权撤回仍会阻断儿童处理并撤销相关设备会话。
- `pending` / `needs_info` 的业务补充和取消沿用 ADR-0007 的状态机；`approved`、`rejected`、`cancelled` 保持终态。留存到期不得自动批准、驳回、取消或推进 revision。
- 同一孩子的当前有效设备和有权监护人可以按 ADR-0007 的既有服务端规则执行各自允许的业务动作，但只有实际来源设备可以按 ADR-0010 恢复设备动作的历史幂等回执。该既有服务端能力没有证明“来源设备存在结果未知意图时，peer 或监护端的语义竞争 mutation 仍然安全”；跨设备/监护端可读当前详情不等于可恢复、接管或并发覆盖来源操作，S20d 不授权客户端开放这种竞争写入。
- `not_observed`、超时、5xx、会话撤销、设备丢失或用户选择都不是 no-effect proof。原逻辑操作不得因此清除恢复意图、改变载荷或换用新幂等键。
- `completed` 只证明历史事件完成；清除精确本地意图后仍必须二读当前详情，不能把历史回执当成当前申请状态。
- ADR-0008 的删除执行仍是 `blocked_policy`。本 ADR 不授权物理删除、去标识、密钥销毁、备份清理或删除作业。
- 正式法律文本、儿童易懂摘要、PIPIA、存量数据整改、逐类留存/删除策略、受托方约束、备份和密钥演练、备案及发布审查全部继续作为生产硬门。

## 术语分离

| 术语 | 本文含义 | 绝不等同于 |
| --- | --- | --- |
| 业务取消 | 将允许取消的积分申请按 ADR-0007 从 `pending` / `needs_info` 推进到 `cancelled` | 清除本地恢复材料、删除数据、撤回授权 |
| 本地意图清理 | 擦除设备上某个精确 mutation intent 的原始载荷和幂等材料 | 服务端未执行、申请已取消、数据已删除 |
| 监护安全放弃 | 对结果未知意图停止继续恢复，并在权威证据允许时清理本地材料的受控流程 | 监护人单方声明 no-effect、跨设备接管原始键、业务取消 |
| 授权撤回 | 终止后续儿童数据处理并撤销相关设备会话 | 自动终结申请、证明历史写操作无效果、完成删除 |
| 数据删除/去标识 | 依据获批逐类策略处理服务端、导出和备份副本 | 业务取消、本地意图清理、安全放弃 |

撤权时为了隐私止损而清除当前设备材料，只能解释为“该设备不再持有材料”，不能解释为“对应服务端动作未发生”。未来 resubmit/cancel coordinator 不得未经本 ADR 接受而复用 S8 创建意图的撤权清理行为。

当前实现存在必须显式评审的不对称：初始 create 正文在第一次 resubmit 后可能只剩请求指纹或旧备份，而每次 resubmit 正文和监护人留言进入不可删除事件长期存在；数据行权导出又只显示当前申请行。该现状不能被描述为已完成最小化、已获批留存或完整披露。

## 监护安全放弃候选方案

“监护人已确认”只能是授权证据的一部分，不能替代服务端事实。候选方案如下，当前均未获实施授权：

| 候选 | 可证明的事实 | 安全评价 | 当前状态 |
| --- | --- | --- | --- |
| 仅客户端弹窗 + 监护人确认 | 只证明有人操作过客户端，不能证明请求从未执行 | 不足；不得清结果未知意图或换键 | 排除为单独依据 |
| 持久、抗回滚的 never-dispatched 证明 | 若实现正确，只能证明本设备尚未发送精确操作 | 可作为本地丢弃候选；仍需决定授权、审计和设备丢失语义 | 待评审、未实现 |
| ADR-0010 的精确 `completed` 回执 | 证明唯一历史事件已完成 | 已可清精确意图；这属于完成恢复，不是安全放弃 | 既有规范性路径 |
| 服务端线性化 abandonment tombstone/fence | 若与原 action、来源 binding、request ID、expectedRevision、载荷指纹和键摘要在同一权威串行点竞争，tombstone 先成立才可能阻止以后执行并证明 no-effect | 是 dispatch 后结果未知场景的候选技术前提；必须处理事件先赢、重复授权、恢复备份和跨副本一致性 | 待产品/合规/安全评审，未设计或实现 |
| 客服或管理员手工标记 | 只证明人工受理，不能证明分布式执行结果 | 除非最终落到同一权威证据或 fence，否则不足 | 不得作为旁路 |

任何未来 fence 也不能复用家庭管理员身份代替监护授权，不能接受 peer 设备上传来源设备的原始幂等键或正文，不能绕过当前授权/隐私/会话门继续处理儿童数据。来源 intent 未取得 completed、权威 no-effect、fence 或 ownership transfer 前，peer 的重叠 mutation 和监护端的竞争 request_info/approve/reject 必须继续阻断；若未来允许，原操作与竞争操作必须由同一权威线性化点排序，不能依赖设备端与监护端各自观察。

## 备份、恢复、导出与日志

- 主库处置不能自动代表备份处置。接受前必须定义备份最大残留窗口、加密与访问控制、到期销毁证据，以及恢复旧备份后重放删除、去标识或 abandonment fence 的机制。
- 删除或去标识不得破坏 ADR-0007 的不可变审批和来源流水约束；若二者冲突，必须先由合规确定可保留的最小证据和正文脱钩方案，再设计前滚迁移。
- 当前行权导出未包含不可变事件中的历史 resubmit/request-info 文字。接受前必须决定这些历史正文是否属于应查阅/导出的儿童数据，并定义说明、格式、访问控制和删除联动。
- 日志继续禁止记录请求 body、原始幂等键、Access/Refresh token、公钥材料和动态儿童正文。未来客服、申诉或安全审计材料若形成新副本，必须纳入逐类留存表。
- 本地应用备份和跨设备同步继续关闭；不得用云同步把来源设备的原始正文、幂等键或 intent 转移给 peer 设备。

## 提议内容（尚非决定）

当前唯一有效结论是继续维持 ADR-0004、ADR-0007、ADR-0008、ADR-0010 与 S20c 的 fail-closed 边界。上面的候选机制和待填表格不构成默认政策、已批准设计或实现授权。

在本 ADR 被接受之前：

1. 不新增 resubmit/cancel mutation UI、operation reconcile 消费、持久 mutation coordinator、AssetStore 新槽位、服务端 abandonment API、tombstone/fence、migration 或删除 executor；
2. 不用 TTL、撤权、设备丢失、`not_observed`、用户选择或监护人确认清除结果未知意图、换键或推断 no-effect；
3. 不宣称当前数据行权导出完整覆盖历史正文，也不宣称现有不可变事件已经满足获批留存策略；
4. 不连接生产、真实儿童数据、真实手机号、凭据、签名材料、外部业务服务或部署系统；
5. 不开启任何儿童生产功能门，不侧载或绕过未成年人模式。

## 接受门槛

只有同时满足以下条件，才可以在一个独立、显式提交中把 ADR-0011 从索引“提议中”原子移动到“已接受”，或创建明确替代本提议的已接受 ADR：

- 逐类留存表所有“待定（阻断）”均填入精确、可执行且有依据的值，覆盖各状态、争议冻结、撤权、删除、终止、备份和恢复；
- 监护授权决策表全部关闭，明确主体、关系、scope、专用重新认证、多监护人冲突、来源设备丢失、跨设备最小披露、一次性和审计回执；
- 产品负责人、合规/法务和安全负责人给出可核验批准证据，PIPIA、正式告知、儿童易懂说明、申诉/投诉和受托方责任同步更新；
- 决定历史事件正文的查阅/导出范围，并给出当前不对称留存的整改方案；
- 若采用权威 fence，先完成单独协议威胁建模，证明其与原 mutation 在线性化点竞争、跨备份恢复仍有效、不会跨家庭/儿童/设备泄露或形成旁路；
- 明确记录后续实现必须另开主题分支，并把迁移、服务、API、HarmonyOS 持久状态、并发、崩溃、结果未知、撤权、跨设备、备份恢复和数据行权测试列为该实现切片的强制验收；接受 ADR 本身不等于实现、部署或生产授权。

任何一项缺失时，状态继续保持“提议中（未接受，不授权实施）”。

## 影响

- S20d 把散落在申请行、不可变事件、设备意图、导出和备份中的文字及证据放入同一评审边界，暴露了现有历史正文保留与导出范围的不对称。
- 结果未知恢复与数据留存被拆开：可以保留审计证据，但不能据此擅自清本地意图；也可以为隐私清理设备材料，但不能据此宣称服务端未执行。
- 监护人授权被限定为受控流程的一部分，不会成为客户端单方 no-effect 声明或跨设备幂等身份转移的捷径。
- 当前代码、迁移、API、HarmonyOS 存储、功能门、生产和发布状态均不变化。

## 后续动作

- 由产品、合规/法务和安全负责人逐项填写并签批两张决策表；在此之前不进入 coordinator/UI 实现。
- 由数据权利流程决定历史 resubmit/request-info 文字的查阅、导出和删除说明，且不得把本提议当成已完成整改。
- 如选择权威 abandonment fence，另行形成协议 ADR/威胁模型和 synthetic 并发参考测试；不得在本提议中预先实现。
- 继续完成正式法律文本、儿童易懂摘要、PIPIA、存量数据整改、受托方、备份/密钥、备案和 AppGallery 正式发布硬门。

## 明确不授权的范围

本 ADR 的编号、文件位置、评审表和未来候选均不授权 mutation、对账消费、持久 coordinator、按钮、API、迁移、删除、部署、生产联网、真实数据处理、儿童设备侧载或儿童功能开放。
