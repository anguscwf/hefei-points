## 本轮实现

### 1. S17 历史回执只读恢复

`scripts/support/synthetic-authorization-consumer.js` 新增生产 API：

```text
recoverSyntheticAuthorizationReceipt(environment, document)
```

它只接受精确原 S17 consumption request，并使用 SQLite read-only、`query_only` 和普通读事务：

- 历史 consumption 返回既有 replay 语义；
- 历史 rejection 恢复原稳定错误，包括 `SYNTHETIC_EXTERNAL_APPROVAL_*`；
- 同 request 不同指纹返回幂等冲突；
- 不存在返回 `SYNTHETIC_AUTHORIZATION_LEDGER_HISTORICAL_RECEIPT_REQUIRED`；
- consumption/rejection 两表同 request 双命中视为完整性破坏；
- 不调用 checkpoint/approval verifier，不推进 checkpoint，不写 receipt/rejection/block，也不回退到消费入口。

read-only recovery 开库前后均拒绝 S17 `-journal/-wal/-shm`；任一 DELETE journal 返回 BUSY，不由只读路径删除或恢复。sidecar 使用 `lstat` 检测，dangling link 不能被 `existsSync` 漏过。production/test-only ledger 双向隔离。

### 2. 独立本地协调意图 journal

新增：

```text
npm run prepare:synthetic-authority-coordination-intent
```

CLI 要求：

```text
SYNTHETIC_AUTHORITY_COORDINATION_INTENT_ACK=prepare-local-intent-not-submitted-v1
```

它只从非 TTY stdin 接受最多 1 MiB 的单行 canonical JSON。journal 固定名 `synthetic-authority-coordination-intent.sqlite`，最大 16 MiB，必须位于仓库、synthetic 数据根、策略和 S17 ledger 之外的批准直接父目录。

首次 journal 不存在时先只读恢复并规范化 S17 receipt，成功后才排他创建 journal，故 missing/rejection 不产生 journal family。既有 journal 先完整校验并恢复精确 S18 replay，再决定是否读取 S17。

journal 只保存摘要与非敏感元数据，绑定：

- 原 S17 consumption document 摘要和本地 receipt；
- ledger、consumer、target；
- policy、checkpoint；
- subject、candidate、source commit、implementation tree、configuration；
- approval、grant ID 和 grant envelope；
- receipt consumption/valid-until 与本机 preparation observation。

不保存原 request、签名束、策略正文、证据正文、路径或凭据。

### 3. 状态、幂等与本地唯一性

唯一持久状态与 result 均为 `locally_prepared_unsubmitted`。本次调用事件由 `outcome=prepared|replayed` 区分。

- 同 request、同指纹精确重放，不再次读取 S17；
- 同 request、不同指纹稳定冲突；
- receipt、grant、grant envelope、approval envelope 和 target/source/tree/config 元组分别唯一；
- commit 前故障回滚；commit 后无法证明时返回 `RESULT_UNKNOWN`，精确原请求可恢复；
- 新记录的本机观察时间不能早于 receipt consumption 或本 journal 历史 preparation 高水位；这只防本 journal 内时钟倒退，不构成可信时间。

journal identity 有意不绑定单一 ledger，使同一文件可对多个本地 ledger 执行冲突检测；因此输出固定：

```text
journalIdentityBoundToSingleLedger=false
crossLedgerUniquenessOnlyWithinThisJournal=true
externalRollbackAnchorVerified=false
globalConsumptionVerified=false
```

复制、回滚、删除或新建另一 journal 都不受外部锚保护，不得把本地唯一性解释成跨主机或全局消费。

### 4. SQLite 崩溃与物理写语义

S18 journal 固定使用 DELETE/FULL 和 `BEGIN IMMEDIATE`。WAL/SHM 永久拒绝；仅本 journal 自己安全、普通、单链接的 DELETE journal 可由 SQLite 可写入口恢复。恢复后必须重新验证 schema、identity、trigger、行摘要和唯一索引。

输出不再用含糊的“journal 未写”描述 replay：

```text
operations.coordinationIntentRowInserted=<本次是否新增 intent 行>
operations.localIntentJournalOpenedWritable=true
```

第二项明确涵盖 SQLite 可能执行 rollback-journal recovery；它仍不表示外部提交或部署。

### 5. 始终未授权、零网络、零部署

首次准备和历史 replay 都固定：

```text

productionChildGateState=not_observed

checks.latestCheckpointExternallyConfirmed=false
checks.globalConsumptionVerified=false

operations.networkAccessPerformed=false

```

支持模块没有 HTTP/HTTPS/net/TLS/DNS/fetch/child-process、部署器、PM2、服务启动或生产数据库路径。
