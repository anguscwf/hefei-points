## 本轮实现

### 1. 只允许当前已加载的唯一 canonical 申请

`ChildSessionCoordinator` 的 `ChildApiPort` 接入 S20a 已有 `getPointRequest` client。`loadPointRequestDetail(pointRequestId)` 只接受当前内存申请列表中恰好一条匹配、且满足 `point_request_<32 位小写十六进制>` 的 ID；畸形 ID、未加载 ID 或列表内重复 ID 都在发网前以 `LOCAL_REQUEST_INVALID` 拒绝。

用户必须在现有“我的申请”列表中手动点击“查看最新详情”才会发起 GET。界面没有任意 ID 输入、自动轮询或后台预取；`Index` 也不展示 `clientRequestId` 或内部申请 ID。

### 2. 内存 selected detail 与单调原位更新

详情只保存在协调器和 `Index` 的内存 selected state。服务端响应仍由 S20a strict parser 绑定精确请求 ID；协调器再验证申请与规则快照身份、申报分值、发生/提交时间、重复标记及来源设备可见的 `clientRequestId` 不变。

revision 必须单调：

- 小于当前列表 revision：`PROTOCOL_ERROR`；
- 等于当前 revision：状态、批准分值、description、家长补充请求、处理决定和 `updatedAt` 必须逐项相同，任何漂移都 fail closed；
- 大于当前 revision：旧状态必须非终态，且 `updatedAt` 表示的真实时间点必须严格前进，随后只原位替换同一列表项并设为 selected detail，不插入第二条记录。不同 UTC offset 的等价或倒退时间不能借字符串排序绕过。

界面只显示当前状态、规则快照、说明、申报/批准积分、疑似重复提示、家长留言/处理说明及相关时间。按钮只有“查看最新详情”和“收起详情”；收起会清除内存 selected detail，不执行任何服务端动作。

### 3. 会话轮换、撤权与生命周期

详情读取沿用既有设备会话：正常先使用当前 Access；若服务端精确返回 `ACCESS_TOKEN_EXPIRED`，最多执行一次既有 proof/Refresh 安全轮换，再以同一个申请 ID 重试一次。它不创建新的业务幂等键或写意图。

协调器通过 operation/detail generation 阻断并发和迟到响应。进入后台会推进 generation、清空全部业务视图和 selected detail；收起详情也会推进 detail generation。下一次请求收到确定性 `SESSION_REVOKED` / `CONSENT_REQUIRED`，或收到儿童处理阻断时，继续复用既有 fail-closed 清理；本地 generation 已推进后，旧响应不能重新暴露详情。客户端没有主动撤权推送，远端已线性化完成、随后才发生的撤权仍须由下一次请求或生命周期切换触发本地清理。未决申请创建 intent 存在时，详情按钮保持不可用，不绕过原 S8 恢复流程。

### 4. 静态隔离 S20a 对账与既有 mutation

HarmonyOS 静态词法门扫描 `entry/src/main/ets` 下全部 `.ets`/`.ts` 消费层源码，只排除承载 S20a 协议基座的 `network/ApiClient.ets` 与 `network/ApiContracts.ets`，并要求 `pages/Index.ets` 和 `session/ChildSessionCoordinator.ets` 必须存在于检查集合。所有被扫描文件都拒绝下列直接符号或字面路径：

- `reconcilePointRequestOperation` 和任何 `PointRequestOperation*` DTO；
- resubmit/cancel mutation 方法或动作；
- `PATCH` 与 `/api/v2/point-requests/:id` 写路径；
- 两个 `/api/v2/me/point-request-operations/*/reconcile` 路径。

静态回归包含第三个消费层 helper 直接调用 operation client 的对抗夹具，避免只检查两个已知文件。该门是词法 defense-in-depth；未来若新增 foundation wrapper、别名或计算属性，仍须人工复核 import/call graph，不能把正则扫描当作语义证明。S20a 的 operation reconcile 仍只存在于底层协议/client 基座和对应测试中。因为 S20b 没有合法的原 resubmit/cancel 持久 intent，任何消费层代码都不得制造对账输入或把该基座变成可操作入口。
